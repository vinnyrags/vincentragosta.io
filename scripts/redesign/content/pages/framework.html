01 / Architecture

Modular by design.

The platform is built on three layers, each distributed as a Composer package through a private Satis registry. At the foundation is Mythus, a theme-agnostic mu-plugin framework that owns the provider pattern, the dependency injection container (PHP-DI), the contracts system, and every support manager. Above that sits IX, a parent theme that bridges Mythus to Timber and Twig for templating. The child theme extends IX with site-specific functionality. Every new project starts from the same foundation — and improvements flow back upstream through the registry.

At the core is the provider — a self-contained domain that owns its PHP classes, assets, blocks, configuration, and tests. Like a Laravel service provider, each one is scoped to a feature and composes its own managers for assets, blocks, features, ACF fields, and REST endpoints. No deep inheritance chains, no tangled dependencies.

03 / Feature system

Features you can turn off and hooks you can't accidentally break.

Functionality is organized into two categories — Features and Hooks — each with distinct inheritance rules that prevent accidental breakage across projects.

Toggle-able

Features

Capabilities that child themes opt in or out of with a single line. Disable comments, restrict block types, enable SVG uploads, activate scroll animations — all controlled declaratively. The DI container resolves each feature and autowires its dependencies.

// ThemeProvider.php
protected array $features = [
    ButtonIconEnhancer::class,  // opted in
    ScrollReveal::class,        // opted in
    WpFormsBaseStyles::class,   // opted in
    // DisablePosts::class => false, (opt out)
];

Always-active

Hooks

Structural behavior that should never be accidentally disabled — icon enhancements, block style variants, social icon configuration. Inheritance is purely additive: parent and child hooks merge automatically, with no opt-out syntax.

// ThemeProvider.php (IX)
protected array $hooks = [
    AccordionIconEnhancer::class,
    FeaturedImageFocalPoint::class,
    HeadingBlockStyles::class,
];

Runtime validation

Place a Feature in the hooks array or a Hook in the features array, and the system warns you at runtime and skips the class. Wrong marker interfaces are caught immediately — not silently ignored.

04 / Block architecture

Each block owns its full pipeline, from editor to frontend.

Custom blocks are WordPress dynamic blocks with the full editor-to-frontend pipeline: React/JSX components in the block editor, PHP + Twig for server-side rendering, and scoped SCSS for styling in both contexts. Each block lives inside its provider's blocks/ directory with a predictable file structure.

blocks/projects/
├── block.json
├── editor/
│   └── index.js
├── render.php
├── style.scss
├── projects.twig
└── view.js
  • block.json — standard block metadata: name, category, supports, and the rendering entry point.
  • editor/ — React/JSX components. WordPress package imports (@wordpress/blocks, @wordpress/element) map to globals at build time, so WordPress internals are never bundled.
  • render.php — the server-side entry point. Receives block attributes, builds a Timber context, and renders a Twig template.
  • style.scss — block styles applied on the frontend and in the editor.
  • {name}.twig — the Twig template the renderer consumes.
  • view.js — optional frontend interactivity (vanilla JS, no framework).

ACF block support

Some blocks use Advanced Custom Fields for structured content entry — giving editors a familiar field-based interface while the developer retains full control over rendering.

05 / Build system

One build script shared across every theme.

A single canonical build script lives in the parent theme. It auto-discovers every provider's assets and blocks, compiles them in parallel, and outputs production-ready CSS and JavaScript. The child theme invokes the same script — no copies, no drift.

  • Any theme — the script uses process.cwd() as the theme root, so it works for any theme that calls it.
  • Sass — compiles provider and block SCSS with configurable load paths, so child themes resolve parent partials (like breakpoints) without duplication.
  • esbuild — bundles JavaScript targeting ES2020, minified in production with sourcemaps in development.
  • Externals — block scripts reference wp.blocks, wp.element, and friends as globals instead of shipping them in the bundle.
  • Watch mode — watches provider assets/ and blocks/ directories and rebuilds only what changed.

06 / Testing

700+ automated tests across three layers of the stack.

Most WordPress projects ship with zero automated tests. This platform has 700+ PHP tests, JavaScript unit tests with DOM assertions, and end-to-end browser automation with automated accessibility audits.

PHP · unit & integration

PHPUnit + WorDBless

WorDBless loads WordPress without a database, so tests execute in milliseconds. Unit tests are fully isolated; integration tests exercise hooks, filters, and the full registration lifecycle.

Test directories mirror source exactly: src/Support/Asset/AssetManager.php is tested at tests/Unit/Support/Asset/AssetManagerTest.php. A HasContainer trait builds a real DI container — no mocking the container itself.

JavaScript · DOM

Vitest + Testing Library

Frontend JavaScript runs in jsdom and is tested against real DOM behavior. The parent theme ships a shared config and setup file — including mocks for the browser APIs jsdom lacks (IntersectionObserver with a trigger() helper, window.matchMedia) — and the child theme inherits it.

End-to-end · accessibility

Playwright + axe-core

Tests run against the live local site in a real browser — real rendered HTML, real interactions. Every page is audited against WCAG 2.1 AA with axe-core, and any violation fails the suite. Accessibility isn't aspirational; it's enforced.

An example of what's covered

  • Dropdown — ARIA toggles, keyboard navigation, focus wrapping, outside-click dismissal.
  • Header — header-height measurement and the ⌘K / Ctrl+K search shortcut.
  • Contents card — active-section tracking and reading progress.
  • Projects block — filtering, search, and the index/grid views.
  • Smoke tests — every page loads with the expected structure and zero console errors.
  • Interaction tests — the mobile and tablet navigation overlay, focus trapping, and keyboard escape handling at phone and tablet widths.
$ make test
→ phpunit     mythus · ix · theme       ✓ passed
→ vitest      providers + blocks        ✓ passed
$ npm run test:e2e
→ playwright  smoke · header · axe      ✓ passed

07 / Design system

Tokens, defined once.

The visual layer is built on CSS custom properties and Sass utilities — a small, deliberate system that adapts across screen sizes and high-contrast environments without duplicating styles.

  • CSS custom properties as the shared interface — color tokens, the spacing scale, and typography variables are defined once and consumed everywhere.
  • theme.json presets — the same color, type, and spacing presets drive both the editor and the frontend, so what an editor picks is what ships.
  • Responsive breakpoints — 576px, 768px, 992px, and 1440px, with Sass mixins (media(), media-down(), and container() for container queries).
  • Block style variants — editorial choices registered as WordPress block styles (panels, spec tables, terminal code, muted text) that editors select from the block toolbar.

08 / Accessibility

Built in. Not bolted on.

Accessibility is a structural concern, not a cleanup pass before launch. It's enforced at every layer — Sass utilities, template markup, JavaScript behavior, and automated testing.

  • WCAG utility mixins — visually-hidden, forced-colors, high-contrast, and reduced-motion, available to every SCSS file in the system.
  • Reduced motion — scroll-reveal animations respect prefers-reduced-motion. Users who opt out of motion see no animation, not broken animation.
  • Windows High Contrast — forced-colors support keeps interfaces usable in high-contrast environments.
  • Semantic markup — Twig templates use proper heading hierarchy, landmark elements (main, nav, article), and ARIA attributes where semantics alone aren't sufficient.
  • Icon accessibility — injected SVG icons carry aria-hidden="true" to prevent redundant screen reader announcements.
  • Automated audits — Playwright + axe-core runs WCAG 2.1 AA checks against every page as part of the end-to-end suite. Violations fail it.

09 / Security

Hardened defaults. Not optional add-ons.

Security decisions are made once in the parent theme and inherited by every project. They're not configuration options — they're the baseline.

  • SVG sanitization — every SVG upload runs through enshrined/svg-sanitize, stripping scripts, event handlers, and XSS vectors before the file reaches the media library. Uploads are restricted to administrators.
  • Block restrictions — 60+ core blocks are off by default, and embeds are limited to vetted providers. The list is managed as a Feature, so a site re-enables only the blocks it actually uses.
  • Comments removed — the entire comment subsystem is gone: admin UI, menu items, frontend output, and the edit-comments screen redirects away. Not hidden — removed.

10 / Operations

One command for everything.

The entire platform — local environment, builds, tests, deployments, database syncing, pattern exports — is operated through a single Makefile. Every workflow is a make command, and a runbook records the traps the commands can't.

The Make system

The Makefile abstracts DDEV, Composer, npm, WP-CLI, SSH, and rsync behind short, memorable commands — so the developer never needs to remember which tool does what or which flags to pass.

Git push deployments

Deployments are a git push. A bare repository on the server receives the push, and a post-receive hook does the rest — checking out the code, restoring environment config, installing production dependencies, building assets, and fixing file ownership. The branch decides the environment:

  • develop — staging
  • main — production

No CI/CD service in the middle, no container orchestration, no deploy queue. Push to the branch, and the server builds and serves it. The entire pipeline is a shell script — auditable, debuggable, and fast.

Environment sync

The database and uploads move between local, staging, and production with a single command. Each sync exports the database, transfers it over SSH, imports it on the target, runs search-replace to swap URLs, flushes caches and rewrites, and rsyncs the uploads directory. Cleanup is automatic — no temp files left behind on either end.

11 / Developer experience

Predictable patterns. No boilerplate.

There's no setup wizard and no boilerplate generator — just conventions that the build system and the container understand automatically.

  • PSR-4 autoloadingThe namespace matches the directory path exactly. Add a PHP class, run composer dump-autoload, and it's available everywhere.
  • Auto-discovered assetsCreate a provider with an assets/scss/index.scss file and the next build finds it. No manifest to update, no config to edit.
  • Auto-discovered blocksAdd a blocks/{name}/ directory with a block.json and the BlockManager registers it; the build compiles its styles and editor scripts.
  • A feature in one lineCreate a class implementing Feature, add it to the provider's $features array, and the container autowires and registers it.
  • Watch modeReal-time SCSS and JS recompilation during development. Change a file, see the result.
