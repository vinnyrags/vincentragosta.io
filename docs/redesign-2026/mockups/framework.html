01 / Architecture

Modular by design.

At the foundation is Mythus, a theme-agnostic mu-plugin framework that owns the provider pattern, the PHP-DI container, the contracts system, and every support manager. Above it sits IX, a parent theme that bridges Mythus to Timber and Twig. The child theme extends IX with site-specific functionality — and improvements flow back upstream through the registry.

At the core is the provider — a self-contained domain that owns its PHP classes, assets, blocks, configuration, and tests. No deep inheritance chains, no tangled dependencies.

01

Three-layer architecture

Framework, Twig bridge, site. Each a standalone package via a private Satis registry.

02

Provider pattern

Each provider owns its PHP, SCSS, JS, blocks, config, and tests.

03

Composition over inheritance

Providers compose managers as collaborators — no monolithic base.

04

Autowiring-first DI

PHP-DI resolves dependencies. Explicit definitions only where it can't.

03 / Feature system

Features you can turn off. Hooks you can't accidentally break.

toggle-able

Features

Capabilities a child theme opts in or out of with a single line. The container resolves each one and autowires its dependencies.

ThemeProvider.php
protected array $features = [
    ContentPartial::class,        // enabled
    DisablePosts::class => false, // opted out
    ScrollReveal::class,          // opted in
];
always-active

Hooks

Structural behavior that should never be disabled by accident. Inheritance is purely additive — parent and child hooks merge.

ThemeProvider.php
protected array $hooks = [
    AccordionIconEnhancer::class,
    HeadingBlockStyles::class,
    FeaturedImageFocalPoint::class,
];
runtime validationPut a Feature in the hooks array — or a Hook in features — and it's caught at runtime and skipped. Not silently ignored.
04 / Block architecture

Each block owns its pipeline, editor to frontend.

Dynamic blocks with React/JSX in the editor, PHP + Twig on the server, and scoped SCSS in both contexts. Some use ACF for field-based entry while the developer keeps full control of rendering.

05 / Build system

One build script, every theme.

A single canonical script lives in the parent theme. It auto-discovers every provider's assets and blocks, compiles them in parallel, and the child theme invokes the same script — no copies, no drift. Watch mode rebuilds only what changed.

07—09 / Built in

Design system, accessibility, security — not add-ons.

07 · DESIGN SYSTEM

Tokens, defined once

  • CSS custom properties as the shared interface
  • theme.json presets for color, type, spacing
  • Block style variants editors pick from
  • Sass breakpoint + container-query mixins
08 · ACCESSIBILITY

Enforced, not aspired to

  • Reduced-motion respected everywhere
  • Forced-colors / high-contrast support
  • Semantic landmarks and heading order
  • axe audits on every page, every run
09 · SECURITY

Hardened defaults

  • SVG uploads sanitized, admin-only
  • Block allowlist — no raw HTML, no embeds
  • Comment subsystem removed, not hidden
  • Inherited by every site, not configured
10 / Operations

One command for everything.

Local environment, builds, tests, deploys, syncing, pattern exports — all through one Makefile. Deploys are a git push: a post-receive hook checks out, installs, builds, and fixes ownership. No CI service in the middle.

make buildall assets

11 / Developer experience

Predictable patterns. No boilerplate.

01PSR-4 autoloading

Namespace matches directory path exactly. Add a class, it's available everywhere.

02Auto-discovered assets

Create a provider with assets/scss/index.scss and the next build finds it.

03Auto-discovered blocks

Add blocks/{name}/block.json and the BlockManager registers it.

04Feature in one line

Implement Feature, add it to $features, and the container wires it.
